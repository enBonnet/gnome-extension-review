# Releasing an Extension to EGO — Packaging, Testing, Upload, Versioning

> Sources: `gnome-extensions(1)` man page, [gjs.guide — Anatomy /
> Translations / Debugging](https://gjs.guide/extensions/), and the EGO
> upload flow on [extensions.gnome.org](https://extensions.gnome.org).
> Curated 2026-09. Use this guide when the user asks to **release, publish,
> package, zip, submit or upload** an extension — run the review workflow
> (SKILL.md) first; release blockers found there must be fixed before packing.

## 1. Release versioning checklist (metadata.json)

Before packing, verify `metadata.json` (full field rules →
`metadata-and-schemas.md`):

- [ ] `version-name` bumped to the release's user-visible version (regex
      `^(?!^[. ]+$)[a-zA-Z0-9 .]{1,16}$` — e.g. `"1.1"`). This is what the
      extension page displays.
- [ ] **No `version` field** (or at most a whole number you did *not* choose —
      it is the EGO upload counter; the site overrides it).
- [ ] `shell-version` lists only **stable** GNOME releases plus **at most one
      development release**; never future/unreleased versions. Check the
      current GNOME release schedule — GNOME ships a new stable every ~6
      months (March/September). Add the newly released stable once you tested
      on it; drop versions you no longer test.
- [ ] `url` present and valid (required by EGO).
- [ ] `gettext-domain` (convention: the uuid) and `settings-schema`
      (convention: `org.gnome.shell.extensions.<id>`) set if used.
- [ ] JSON parses; uuid regex valid; no `gnome.org` namespace.

## 2. Package the bundle

Preferred — the official tool (auto-includes `extension.js`, `metadata.json`,
`prefs.js`, `stylesheet.css`, `stylesheet-dark.css`, `stylesheet-light.css`,
and picks up `schemas/` automatically):

```sh
gnome-extensions pack --out-dir=. --force
# Extras:
#   --extra-source=FILE        include an additional source file/dir
#   --schema=SCHEMA            include a GSettings schema outside schemas/
#   --podir=po                 compile .po files from po/ into the bundle
#   --gettext-domain=DOMAIN    domain for compiled translations
#                              (defaults to metadata gettext-domain, else uuid)
```

Manual fallback (when `gnome-extensions pack` is unavailable) — **files at
the zip root, never nested in a folder**:

```sh
zip -r example@gjs.guide.zip extension.js metadata.json prefs.js \
    schemas/org.gnome.shell.extensions.example.gschema.xml \
    locale -x '*.po' '*.pot' 'schemas/gschemas.compiled'
```

**MUST NOT ship** (R12/R25 — EGO's Shexli pre-review flags these):

- `schemas/gschemas.compiled` — for 45+ packages EGO compiles the schema when
  serving the download; ship only the XML (EGO-P-006)
- `.po`/`.pot` translation sources — ship compiled `.mo` under `locale/` only
- build/install scripts, `node_modules`, `.git`, `__pycache__`, transpiler
  output maps
- binaries of any kind (R12)

Files in the zip that only exist for local builds (compiled schemas, `.mo`
regenerated by pack) should be gitignored in the source repo.

## 3. Validate the bundle

Run the scanner twice — once on the source tree, once on the **built zip**:

```sh
python3 <skill-dir>/scripts/static_checks.py <extension-dir>
python3 <skill-dir>/scripts/static_checks.py example@gjs.guide.zip
```

Zip mode verifies: required files at the zip root (`metadata.json`,
`extension.js`), no nested single-directory wrap, no compiled schema, no
`.po`/`.pot`, no binaries, no build junk, and the zip's `metadata.json`
(`version-name` format, `version` field, `shell-version`).

Then unpack the zip to a scratch dir and spot-check that only intended files
are inside:

```sh
unzip -l example@gjs.guide.zip
```

## 4. Local install and smoke test

```sh
gnome-extensions install --force example@gjs.guide.zip
gnome-extensions info example@gjs.guide     # state: ACTIVE, no errors
gnome-extensions enable example@gjs.guide
gnome-extensions prefs example@gjs.guide    # prefs window opens cleanly
```

Smoke-test checklist (each item is a common EGO rejection when broken):

- [ ] **Enable/disable cycles** — toggle in the Extensions app several times;
      no duplicated UI, no errors (lifecycle symmetry).
- [ ] **Session-mode cycles** — lock and unlock the screen; with
      `unlock-dialog` in `session-modes`, verify behavior on the lock screen.
- [ ] **Prefs open/close** — open prefs twice; no leaks/warnings
      (`close-request` cleanup, R34).
- [ ] **Logs are clean** — `journalctl -f -o cat /usr/bin/gnome-shell` while
      exercising the extension; no errors or tracebacks from your uuid.
- [ ] **Looking Glass** — `Alt+F2` → `lg` → *Extensions* tab for state and
      errors.
- [ ] **Shell restart** — X11: `Alt+F2` → `r`; **Wayland has no in-place
      restart — log out/in**. Verify the extension survives a fresh login.
- [ ] Test on the **oldest** GNOME version claimed in `shell-version` when
      possible (or drop versions you cannot test).

## 5. Translations (if any)

- `gettext-domain` in metadata (convention: the uuid); mark translatable
  strings with `gettext`/`_` from
  `resource:///org/gnome/Shell/Extensions/js/extensions/prefs.js` (prefs) or
  the shell-side equivalent.
- Keep sources in `po/` (`<lang>.po`, generated from a `.pot`); **do not ship
  them** — `gnome-extensions pack --podir=po` compiles them into
  `locale/<lang>/LC_MESSAGES/<domain>.mo` inside the bundle.
- Manual compile fallback:
  `msgfmt po/de.po -o locale/de/LC_MESSAGES/<domain>.mo`.
- The `.mo` filename must equal the gettext domain (which is why using the
  uuid as domain is the safe convention).

## 6. Submit to extensions.gnome.org

- Submission is **web-only — there is no public upload API**. Prepare the
  zip and hand it to the user with these steps; do not claim to have
  uploaded anything.
- User flow: log in at <https://extensions.gnome.org> → *Upload extension*
  → select the zip. The site reads `metadata.json` for name/description.
- An **icon** for the extension page is set on the site (not part of the
  zip).
- Before upload, confirm from the review side: license is GPL-compatible
  (R23), code taken from other extensions carries attribution (R23), the
  AI-generation notice is **removed** (R16 — its presence in an upload gets
  flagged), and name/description violate neither the GNOME CoC (R21) nor
  trademarks (R24).
- A first submission stays unpublished until a reviewer approves it.

## 7. After submission — the review

- The upload first passes **Shexli**, EGO's static analyzer. Warnings it
  reports should be fixed and re-uploaded before a human ever looks — see
  the cross-reference table in `review-guidelines.md` (Appendix) to map
  findings to this skill's rules.
- Human review is asynchronous (days to weeks). Respond on the review
  thread; keep requested diffs **small** — reviewers prioritize small diffs.
- **A new upload supersedes a pending review.** While a version is
  "Unreviewed" you may upload again; only the newest upload gets reviewed.
  Leave a note on the review thread that the newest upload replaces it and
  summarize what changed since the last look.
- Rejected versions remain listed forever; fix the findings and re-upload —
  the internal counter increments regardless (your `version-name` keeps the
  project's own semver).

## 8. After approval — maintenance

- Publishing on EGO is an agreement to **maintain** the extension.
- Updates follow the same flow: review → version checklist → pack →
  validate → upload. Fixes for reviewers' comments re-upload the same way.
- GNOME ships a new stable every ~6 months: check the porting guide
  (`https://gjs.guide/extensions/upgrading/gnome-shell-<NN>.html`), test on
  it, then add it to `shell-version`. A GNOME release that breaks the
  extension without an update is the most common cause of user reports.
- If you stop maintaining it, say so on the page rather than leaving a
  broken extension published.

## 9. Release checklist (condensed)

```text
[ ] review workflow passed (SKILL.md), AI notice removed if applicable
[ ] metadata: version-name bumped, no version field, shell-version valid
[ ] static_checks.py <dir>            — no unverified blockers
[ ] gnome-extensions pack (or manual zip, files at root)
[ ] static_checks.py <bundle>.zip     — zip mode clean
[ ] local install + smoke test (§4), clean journalctl
[ ] zip handed to user; upload at extensions.gnome.org (web-only)
[ ] Shexli warnings fixed; review thread answered; note on re-uploads
```
